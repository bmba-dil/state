## Decisions Made

- **Reuse `RefreshLockTimeout` (no new `VaultLockTimeout`):** the lockfile is the same `<vault>.lock`, the timeout semantics are identical, and a sibling exception type would force callers (Typer commands) to `except` both — strictly worse UX. The class name reads "refresh lock" but its current docstring already describes it as "the refresh lock could not be acquired"; that wording remains accurate now that "the refresh lock" is the same on-disk lock used by CLI ops.
- **Sync wrapper, not async:** `cli_ops.login()` and `cli_ops.logout()` are `async def`, but their RMW blocks are pure-Python (no `await` inside). A sync context manager works correctly inside an async body via `with` (NOT `async with`), and works in CLI thread workers that have no event loop. An async wrapper would force every caller to manage an event loop just to take the lock.
- **Lock scope = persistence ONLY:** `_emit_auth_event` stays OUTSIDE the lock for both login and logout. Events dual-write to SQLite + SyncEvent which can be slow; holding the lock during those writes would block all other writers unnecessarily. Vault mutation is atomic within the `with` block; events are independent.
- **`status()` is unchanged:** read-only path. Per `CONTEXT.md` "status() does NOT trigger refreshes", and per the deviation_rules SCOPE BOUNDARY clause, we leave it alone.
- **Test concurrency via threads (not processes):** the GIL does NOT prevent the `load_vault → save_vault` interleave (the syscall-bound region releases the GIL implicitly). Threads are deterministic and ~10× faster than `multiprocessing` (no fork overhead). The test asserts lock semantics, not GIL semantics, so threads suffice.
- **`poll_interval=0.05` included in `_new_sync_lock` and `with_vault_lock`:** verified that `filelock>=3.20.3` (we have 3.29.0) accepts `poll_interval` on `FileLock.__init__`. Symmetry with `_new_async_lock` is preserved.
