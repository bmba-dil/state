## Worth Knowing

### IN-01: Parent-directory lstat → os.open is still TOCTOU-vulnerable

**File:** `src/state_core/auth/store.py:235-251`

**Issue:** `_atomic_write` performs `path.parent.mkdir(...)` then `os.lstat(path.parent)` then `os.open(tmp, ..., O_NOFOLLOW)`. `O_NOFOLLOW` protects only the leaf component (`tmp`'s final path segment). An attacker who can race between the `os.lstat` and the `os.open` to swap `path.parent` for a symlink (or to swap an intermediate ancestor) can still redirect the write — the kernel resolves the prefix at `os.open` time, and `O_NOFOLLOW` does not check intermediate components on Linux/macOS.

The truly race-free fix is `os.open(parent, O_DIRECTORY | O_NOFOLLOW)` once, then `os.openat(parent_fd, tmp_basename, O_WRONLY | O_CREAT | O_TRUNC | O_NOFOLLOW, 0o600)` for the tmp file, then `os.replace` via `os.rename` semantics relative to the same dir fd. This eliminates the prefix-resolution race entirely.

**Why this is INFO not WARNING:** the threat model for `.state/` assumes a non-adversarial local FS (per refresh.py rule 6 and the broader `.state/` threat model). The current defense already raises the bar substantially — defeating it requires a local-FS attacker who can both write to the parent of `.state/` AND win a microsecond race against `_atomic_write`. T-018-9 is documented as a LOW-severity threat, so the residual TOCTOU is consistent with the milestone's risk acceptance.

**Fix (optional, future hardening):**
```python
# Sketch — requires careful errno handling
parent_fd = os.open(path.parent, os.O_DIRECTORY | os.O_NOFOLLOW)
try:
    fd = os.open(
        tmp.name,  # basename only
        os.O_WRONLY | os.O_CREAT | os.O_TRUNC | os.O_NOFOLLOW,
        VAULT_MODE,
        dir_fd=parent_fd,
    )
    # ... write/fsync/close ...
    os.replace(tmp.name, path.name, src_dir_fd=parent_fd, dst_dir_fd=parent_fd)
finally:
    os.close(parent_fd)
```

Track as a hardening item if/when the threat model widens.

### IN-02: `with_vault_lock` finally-touch can run after a failed acquire

**File:** `src/state_core/auth/refresh.py:218-237`

**Issue:** The `try/finally` structure is:

```python
try:
    try:
        with lock:
            yield lock_path
    except filelock.Timeout as exc:
        raise RefreshLockTimeout(lock_path) from exc
finally:
    try:
        lock_path.touch(exist_ok=True)
    except OSError:
        pass
```

If `lock.__enter__` raises `filelock.Timeout`, control unwinds through both excepts and into the `finally`, where `lock_path.touch(exist_ok=True)` runs. On a clean acquisition-timeout path, this creates (or re-creates) the lockfile even though we never owned it. Concurrent acquirers tolerate this (they use `O_CREAT`), so the impact is purely cosmetic noise.

The same shape exists in `read_credential` (line 302-309) and `refresh_credential` (line 408-415), so this is consistent with the established pattern — the comment "filelock 3.29 unlinks the lockfile on release; re-create it so tooling can still observe its presence" applies. Worth knowing; intentional.

**Fix (if desired):** gate the touch on a "lock was acquired" boolean set inside the inner `with`. Probably not worth the complexity given the consistent pattern.

### IN-03: `with_vault_lock` does not lstat the lockfile path itself

**File:** `src/state_core/auth/refresh.py:212-237`

**Issue:** `with_vault_lock` constructs `filelock.FileLock(str(lock_path), ...)` where `lock_path = <vault>.lock`. There is no symlink check on `lock_path` before acquisition, and `lock_path.touch(exist_ok=True)` in the finally follows symlinks. An attacker who plants a symlink at `<vault>.lock` could redirect lock acquisition to an attacker-controlled path — defeating the cross-process serialization guarantee that `with_vault_lock` is supposed to provide.

This is symmetric to T-018-9 but for the lockfile sibling rather than the vault file itself. The same threat-model assumption from IN-01 applies (non-adversarial local FS), so this is informational only.

**Fix (optional):** add an `os.lstat(lock_path)` + `S_ISLNK` check before constructing the `FileLock`, raising `AuthVaultSymlinkError(lock_path)` on hit. Mirror in `_new_async_lock` and `_new_sync_lock` for completeness.

### IN-04: `logout()` `account_id[:12]` slicing can over-match short prefixes

**File:** `src/state_core/auth/cli_ops.py:341`

**Issue:** Pre-existing behavior, NOT introduced by Phase 022.2, but adjacent to the touched RMW window so worth flagging:

```python
or _prefix12(c).startswith(account_id[:12])
```

If a caller passes a short `account_id` (e.g., `"key"` — 3 chars), every credential whose first-12-char prefix starts with `"key"` matches. The concurrent-logout regression test (`test_concurrent_logout_no_clobber`) deliberately uses `"key-{idx}-not"` (12 chars exactly) to avoid this, but a real CLI user passing `--account key` could accidentally remove unintended credentials.

The match is already constrained by the `len(matches) > 1` ambiguity check (line 346-351), which raises `ValueError`. So the worst case is a false-negative ambiguity error rather than silent wrong-cred deletion. Acceptable, but consider documenting a minimum prefix length or requiring an exact match for short inputs in a future iteration.

**Fix (if desired, future):**
```python
# Require account_id to be at least N chars OR exact-match to one of the existing fields.
if len(account_id) < 8 and not any(... exact matches ...):
    raise ValueError("--account requires at least 8 characters or an exact account_id/email match")
```

## Items Verified Clean

- **chmod 0600 invariant:** all writes still flow through `_atomic_write`; new symlink checks fail-closed before any data hits disk.
- **`AuthVaultSymlinkError` message hygiene:** `__init__` constructs the message from `path` only; STORE-22e explicitly asserts no credential bytes leak (`sk-ant`, `sk-ant-oat`, `sk-ant-api03`, `ya29.`).
- **Mode isolation:** `store.py`, `refresh.py`, `cli_ops.py` import only stdlib + filelock + orjson + pydantic + structlog + `state_core.auth.*`. No cross-mode imports.
- **Reentrant-deadlock contract:** `with_vault_lock` docstring (rule 10 in refresh.py) clearly forbids nesting and forbids overlap with `_new_async_lock` for the same vault path; `cli_ops.login` / `cli_ops.logout` are the only callers and they each do exactly one acquisition per call.
- **Event-emission ordering:** `_emit_auth_event` correctly runs OUTSIDE the lock in both `login` and `logout` (line 286, 372-373) — keeps lock-held time short and matches the documented "vault mutation atomic; mirroring may be slow" contract.
- **Concurrent-writer regression tests:** thread-pool driven, assert exact set equality on persisted credentials (not just count) — strong enough to detect lost-update or stale-read clobbers.
- **`ensure_initialized` symlink check:** `path.is_symlink()` (which uses `os.lstat` internally) runs BEFORE `_verify_mode`, so a symlink is rejected with `AuthVaultSymlinkError` rather than silently following the link.
- **POSIX-only mode check still skips on Windows** (line 188-203) but the symlink check now runs cross-platform — correct: symlink rejection is valid on every OS Python supports.
- **`O_NOFOLLOW` errno translation:** ELOOP correctly translated to `AuthVaultSymlinkError`; non-ELOOP `OSError` re-raises unchanged (line 248-251). Good.
- **Pydantic invariant assertion** in `save_vault` (line 308-310) preserved — array-per-provider P1-7 defense intact.
