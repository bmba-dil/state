<objective>
Add `validate_daemon_path()` to the daemon middleware module and extend `ModeMiddleware` to expose
subtree enforcement as a callable layer. This is the 2nd layer of 6-layer defense-in-depth for mode isolation.

Purpose: After the CLI creates `.state/build/` and `.state/teach/` subtrees (Plan 098-01), the daemon must
enforce that write operations target only the correct subtree. This is a physical, non-bypassable enforcement
layer — even if the HTTP header (layer 1) passes, the actual filesystem path is validated before any write.

Output: `validate_daemon_path()` function in `src/state_daemon/middleware.py` that raises `ValueError` when
a filesystem path crosses into the wrong subtree. This function is the canonical enforcement point that all
daemon write handlers call before performing file I/O.
</objective>

     ```python
     def validate_daemon_path(path: str | Path) -> None:
         """Validate that *path* is within the daemon's active-mode subtree.

         Reads the active mode from the cached ``ModeConfig`` (loaded at daemon
         startup via ``load_mode_config()``).  Delegates to
         ``state_core.schema.validate_subtree_path()`` for the actual prefix check.

         Call this BEFORE any daemon write operation that touches a mode-specific
         file.  The call is a hard gate — if it raises ``ValueError``, the write
         MUST be aborted and the request rejected with a 403.

         Paths in the ``.state/`` root (``mode.json``, ``events.sqlite``, etc.)
         are always allowed — they are shared kernel files.

         Args:
             path: A filesystem path (string or ``pathlib.Path``).

         Raises:
             ValueError: If *path* crosses into the wrong subtree for the
                         currently active daemon mode.
                         Also raises if ``get_current_mode()`` returns an
                         unrecognised value (e.g., empty string or a stale
                         corrupted config).
         """
         active_mode = get_current_mode()
         validate_subtree_path(path, active_mode)
     ```

     Implementation notes:
     - Use `str | Path` as the type annotation (Python 3.10+ union syntax, compatible with 3.12+)
     - The function is intentionally thin — all logic delegates to `schema.validate_subtree_path()`
     - `get_current_mode()` returns `"both"` if config hasn't been loaded yet (permissive default)
     - No additional error message wrapping needed — `validate_subtree_path()` already produces
       messages like `"Path '.state/build/foo' is not in the 'teach' subtree"` (exact message
       format is up to the executor, but must include the rejected path and the active mode)

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| daemon handlers → filesystem | Write operations cross this boundary; validate_daemon_path() must gate every write |
| ModeConfig cache → validate_daemon_path | The cached active mode is the enforcement signal — cache integrity is critical |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-098-07 | Spoofing | validate_daemon_path | mitigate | Reads active mode from `get_current_mode()` which returns the cached `ModeConfig` loaded at daemon startup — cannot be overridden mid-request by untrusted input |
| T-098-08 | Tampering | ModeConfig cache | mitigate | `_config` is a module-level variable set once by `load_mode_config()` at daemon startup; no write path exists after initial load (the only setter is `load_mode_config`, called during daemon boot) |
| T-098-09 | Repudiation | cross-subtree rejection | mitigate | All rejections raise `ValueError` with explicit message including the rejected path and active mode — logged by the calling handler with structlog for audit trail |
| T-098-10 | Information Disclosure | validate_daemon_path | accept | Error messages include the rejected path (which is filesystem-local) and the active mode — this information is already known to the daemon process; no external leakage |
| T-098-11 | Denial of Service | validate_daemon_path | accept | Function is O(1) string prefix check — no resource exhaustion vector; calling it before every write adds negligible overhead |
| T-098-12 | Elevation of Privilege | both-mode bypass | accept | Both-mode permissiveness is by design — documented in ModeConfig; projects using both-mode are dual-mode by choice, not accident |
</threat_model>
