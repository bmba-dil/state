Create `src/state_core/import_lint.py` with the following structure:

**Data classes:**
- `Violation`: `source_file: Path, line_num: int, import_target: str` — one per forbidden import
- `CheckResult`: `exit_code: int, violations: list[Violation]` — aggregate result

**Core function — `lint(root: Path | None = None) -> CheckResult`:**
- If `root` is None, default to the `src/` directory relative to repo root (find via walking up from this file's `__file__` to find pyproject.toml or `.git`)
- Walk all `.py` files under `src/state_build/`, `src/state_teach/`, `src/state_daemon/`, and `src/state_core/` (not just build/teach — also check that state_core itself doesn't import from either silo)
- For each file, parse with `ast.parse(source_text, filename=str(path))`
- Walk the AST with `ast.walk(node)` looking for `ast.Import` and `ast.ImportFrom` nodes
- For each import node, determine: (a) which package the source file belongs to, (b) which package the import target refers to

**Violation rules (use `pathlib` path prefix checks):**
- Any file under `src/state_build/` importing anything from `state_teach` → VIOLATION
- Any file under `src/state_teach/` importing anything from `state_build` → VIOLATION
- Any file under `src/state_core/` importing anything from `state_build` or `state_teach` → VIOLATION (shared kernel must not depend on mode packages)
- `state_daemon/` importing from either mode → ALLOWED (daemon is shared infrastructure)
- `state_cli/` importing from either mode → ALLOWED (CLI orchestrates both)

**Import target resolution for `ast.Import` nodes (e.g., `import state_teach.mcp`):**
- Extract the module name from `alias.name` — the full dotted path like `state_teach.concepts`
- Check if it starts with `state_teach` or `state_build`

**Import target resolution for `ast.ImportFrom` nodes (e.g., `from state_teach.concepts import Concept`):**
- Use `node.module` — the module string (e.g., `state_teach.concepts`)
- If `node.module` is None (relative import like `from . import foo`), use `node.level` to resolve against the source file's package — relative imports within same package are always allowed

**`__main__` block:**
- `if __name__ == "__main__":`
- Call `lint()`, print each violation to stderr as `{source_file}:{line_num}: forbidden import of {import_target}`, exit with `result.exit_code`

**Module-level docstring** referencing MODE-06 and TST-07.

**API surface exports:** `__all__ = ["lint", "CheckResult", "Violation"]`

Follow all CONVENTIONS.md rules: `from __future__ import annotations` first line, 120-char line limit, double quotes, stdlib imports (ast, pathlib, sys, dataclasses) before third-party.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| file system | The linter reads `.py` files from `src/` — untrusted input in the sense that arbitrary Python source is parsed, but no code is executed |
| CI pipeline | The linter exit code gates merge — a false positive could block development, a false negative could let a mode isolation violation through |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-102-01 | Spoofing | import_lint.py | accept | No network/human actors — tool runs locally on source files, no authentication surface |
| T-102-02 | Tampering | file system input | mitigate | `ast.parse` is a read-only static analysis — source files are parsed, never executed. Malformed Python files cause `SyntaxError`, caught and reported as lint errors rather than crashing |
| T-102-03 | Repudiation | CI pipeline | accept | No transactions or audit trail needed — exit code is binary pass/fail, git blame identifies who introduced the violating import |
| T-102-04 | Information Disclosure | import_lint.py | accept | Tool only reads file paths and import statements — no secrets, no PII, output is file paths + import targets |
| T-102-05 | Denial of Service | import_lint.py | accept | `ast.parse` on all `.py` files under `src/` is sub-second for hundreds of files. No network I/O, no unbounded memory allocation. False-positive blocking merge is a correctness bug, not a DoS — fixed by code review |
| T-102-06 | Elevation of Privilege | CLI invocation | accept | Tool runs with same privileges as the invoking user — reads source files, writes nothing. No setuid, no daemon, no escalation path |

**Overall disposition:** This is a static analysis tool with minimal attack surface. The only practical threat is false negatives (missed violations), which are mitigated by the test suite covering both `ast.Import` and `ast.ImportFrom` node types.
</threat_model>
