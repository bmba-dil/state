<objective>
Implement the opencode `config` hook that reads `.state/mode.json` at boot and dynamically registers/unregisters the `state-build` and `state-teach` MCP servers based on the active mode. Add an `event` hook scaffold for `state.mode.activated` hot-reload.

Purpose: This is layer 3 of 6 for mode enforcement. The `config` hook ensures that only the correct MCP server(s) are registered for the current mode, preventing cross-mode tool leakage at the protocol level.

Output: Two new hook modules (`config.ts`, `event.ts`) + index.ts wiring. The `state-build` MCP server is registered only when mode ∈ {build, both}; `state-teach` only when mode ∈ {teach, both}.
</objective>

  <action>
Create `packages/opencode-plugin/src/hooks/config.ts`. This is the canonical type-safe config hook for MCP registration.

**Implementation:**

1. Import `Hooks` type from `@opencode-ai/plugin` and `log` from `../logger.js`.

2. Define a helper function `readModeConfig(projectDir: string): string | null`:
   - Construct the path: `projectDir + "/.state/mode.json"` (the `Config` hook runs with opencode's project directory context; the hook receives `input: Config` which contains project path info, but for now accept a `projectDir` parameter since the config hook's input doesn't carry directory — use `process.cwd()` as fallback when no explicit path is available)
   - Actually — the `config` hook only receives `input: Config`, not `PluginInput`. There's no project directory in `Config`. Use `process.cwd()` as the project root since the opencode runtime's cwd IS the project directory.
   - Read the file using Bun: `const f = Bun.file(resolve(cwd, ".state/mode.json"))`
   - Check `await f.exists()` — if false, log a warning: `log({msg: "mode.json not found — MCP servers will not be registered", path})` and return `null`
   - Read content: `const text = await f.text()`
   - Parse JSON: `const data = JSON.parse(text)`
   - Validate shape: `data.mode` must be `"build"` | `"teach"` | `"both"`. If missing or invalid, log error and return `null`.
   - Return the validated mode string, or `null` if any step fails.

3. Define a helper function `applyMcpRegistration(mode: string | null, input: Config): void`:
   - Initialize `input.plugin` as empty array if undefined: `input.plugin = input.plugin || []`
   - Remove any existing state-* entries from `input.plugin`. Filter out any entry where the name (string itself, or first element if tuple) starts with `"state-"`. Use: `input.plugin = input.plugin.filter(p => { const name = Array.isArray(p) ? p[0] : p; return name !== "state-build" && name !== "state-teach"; })`
   - If mode is `"build"` or `"both"`: push `"state-build"` onto `input.plugin`
   - If mode is `"teach"` or `"both"`: push `"state-teach"` onto `input.plugin`
   - If mode is `null` (no file or invalid): push nothing — leave both servers unregistered
   - Log the result: `log({msg: "config hook: MCP registration applied", mode, build_active: mode === "build" || mode === "both", teach_active: mode === "teach" || mode === "both"})`

4. Export the hook using the existing pattern:
   ```typescript
   export const config: NonNullable<Hooks["config"]> = async (input) => {
     const cwd = process.cwd();
     const mode = await readModeConfig(cwd);
     applyMcpRegistration(mode, input);
   };
   ```

**Key design decisions:**
- Use `process.cwd()` because the `Config` hook type does not expose project directory — the opencode process's current working directory IS the project root.
- Keep `readModeConfig` and `applyMcpRegistration` as separate functions so the event hook (Task 2) can re-call `applyMcpRegistration` with an updated mode without re-reading the config hook flow.
- Export `readModeConfig` and `applyMcpRegistration` so the event hook can import and reuse them.

**Edge cases handled:**
- File not found → log warning, return null (no MCP servers registered)
- Invalid JSON → catch, log error, return null
- Valid JSON but missing `mode` key or invalid mode value → log error, return null
- Mode is valid but not "both" → only one server registered
- Existing state-* entries from a previous plugin load → filtered before adding correct ones

- However: the `event` hook only has access to `{ event: Event }`, NOT the `Config` object. Since the config object was already consumed at boot time, we cannot re-apply to the same `Config` reference.
- **Strategy:** The event hook logs the mode change and calls `readModeConfig` to validate. When Phase 104 (mode activation event) ships with the daemon SSE event bus, the canonical hot-reload path will use the daemon client API. - Implementation:
  ```typescript
  import type { Hooks } from "@opencode-ai/plugin";
  import { log } from "../logger.js";
  import { readModeConfig } from "./config.js";

  export const event: NonNullable<Hooks["event"]> = async (input) => {
    const eventType = input.event?.type;
    if (eventType !== "state.mode.activated") return;

    log({ msg: "event hook: state.mode.activated received", event: eventType });

    const cwd = process.cwd();
    const mode = await readModeConfig(cwd);
    log({
      msg: "event hook: mode.json re-read for hot-reload",
      mode,
      note: "Full MCP re-registration via daemon client API will be implemented when Phase 104 ships. This scaffold validates the event listener pattern and mode re-read."
    });
  };
  ```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `.state/mode.json` file → Plugin config hook | Untrusted filesystem input — file may be missing, malformed, or contain invalid mode values |
| Plugin config output → opencode runtime | Plugin mutates `config.plugin` array consumed by opencode's MCP initialization |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-099-01 | Tampering | `readModeConfig()` — JSON parsing | mitigate | Wrap `JSON.parse` in try/catch; validate that `data.mode` is exactly `"build"`, `"teach"`, or `"both"` (strict literal check, not loose truthiness). Reject any unknown mode values and extra fields. |
| T-099-02 | Denial of Service | `.state/mode.json` missing at boot | mitigate | Graceful degradation: if file does not exist (`await f.exists()` is false), log a debug warning and return `null`. The config hook pushes zero MCP servers — the plugin continues without MCP functionality rather than crashing. |
| T-099-03 | Information Disclosure | mode value leaked via logs | mitigate | `log()` function is gated behind `STATE_DEBUG=1` environment variable. In production (`STATE_DEBUG` unset), no mode configuration is written to stdout. |
| T-099-04 | Elevation of Privilege | Malformed mode.json could bypass mode restrictions | mitigate | Strict validation: only `"build"`, `"teach"`, `"both"` are accepted. Any other value (including `"kernel"`, which is internal-only per schema.py `ModeConfig`) is rejected as invalid and results in zero MCP servers registered. The enforcement is defense-in-depth — this is layer 3; layer 5 (daemon middleware, MODE-05 already shipped) is the canonical gate. |

## Design Rationale

- **No PII or secrets in mode.json** — the file contains only a single `mode` field. Threat surface is minimal.
- **File-not-exists is NOT an error** — `.state/mode.json` is created by `state mode init` (Phase 103). Before that CLI runs, the absence is expected. The config hook degrades gracefully.
- **Log gating** — `STATE_DEBUG=1` ensures no production log leakage of mode transitions.
- **Defense-in-depth** — this is layer 3 of 6. Even if a threat actor tampers with mode.json to register `state-teach` in build mode, the daemon's HTTP middleware (layer 5, Phase 053) rejects cross-mode events at the canonical gate.
</threat_model>
