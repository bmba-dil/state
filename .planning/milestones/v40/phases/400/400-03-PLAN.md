# Descope and Block Semantics

## Overview
[One paragraph: how the hierarchy handles work that stops being active]

## Abandon Cascade (D-13)
### Trigger
When a Slice or stage is explicitly abandoned via /state-abandon command or
state.{tier}.abandoned event. Applies to Slice, Stage, and Arc tiers.

### Cascade Rules
1. When Slice is abandoned:
   - Slice transitions to `abandoned` state (terminal — no forward path)
   - ALL Slices that `depends_on[{id: "slice-X", edge: "blocks"}]` this Slice
     are automatically marked `blocked` with `blocked_reason: "Dependency slice-X abandoned"`
   - Slice's child Steps are NOT auto-abandoned — they remain in current state
     (Steps persist for audit trail; agent decides whether to abandon individually)
   - Slice's worktree is NOT destroyed — preserved for forensics

2. When Stage is abandoned:
   - Stage transitions to `abandoned` state
   - ALL child Slices transition to `blocked` (not abandoned — manual resolution)
   - ALL same-Arc Stages that `depends_on` this Stage → `blocked`
   - Arc continues processing other Stages

3. When Arc is abandoned:
   - Arc transitions to `abandoned` state
   - ALL child Stages → `abandoned` (direct parent cascade)
   - ALL child Slices → `blocked` (grandchild cascade, stops at Slice level)
   - No cascade to other Arcs (D-10: same-parent-only, and cross-Arc deps are deferred idea)

### No Auto-Cascade-Abandon
Cascade stops at BLOCKED — never auto-abandons dependents. The user must:
- Manually abandon each blocked dependent, OR
- Defer the blocker (D-14), OR
- Re-plan to remove the dependency

### Blocked Reason Format
`blocked_reason` in frontmatter stores a human-readable string:
- "Dependency {id} abandoned" — from abandon cascade
- "Dependency {id} not yet shipped" — standard blocking
- "External condition: {description}" — for non-dependency blocks

## Deferment Strategy (D-14)
### Purpose
Intentional descoping: "I will come back to this later." Unlike abandon
(permanent exit), deferment preserves the work for future re-activation.

### Entry
- Slice status set to `deferred` via state.slice.deferred event
- Requires `deferred_reason` in frontmatter (free-text, human-written)
- Only available from `planned` state. NOT from in_progress or shipped.
  (Slices mid-work must be reverted first, then deferred.)

### Effect on Dependents
Slices that `depends_on[{id: "slice-X", edge: "blocks"}]` a deferred Slice:
- ARE unblocked (treated as "soft-done")
- Proceed with a `deferred_dep` flag in frontmatter:
  `deferred_deps: ["slice-X"]` — projector-owned field
- The `deferred_dep` flag is informational — it does NOT block shipping
- Scheduler treats deferred deps as satisfied for topological ordering

### Soft Edge Behavior (edge: "soft")
When dependency has edge: "soft" (advisory) and source is deferred:
- Scheduler may promote the dependent to earlier execution
- `deferred_dep` flag still set for audit trail

### Data Edge Behavior (edge: "data")
When dependency has edge: "data" (artifact-producing) and source is deferred:
- Dependent CANNOT proceed — data edge requires actual artifact output
- Dependent remains `blocked` until source is undeferred and produces artifacts
- Rationale: "data" edges are hard because the target literally needs the source's files

### Reactivation
- Deferred Slices can be un-deferred: `state.slice.undeferred` → status → `planned`
- `deferred_reason` cleared on un-defer
- All dependents' `deferred_dep` flags removed for this dep on un-defer

### Defer vs Abandon Decision Table
| Criterion | Abandon | Defer |
|-----------|---------|-------|
| Permanence | Permanent exit | Temporary pause |
| Cascade | Dependents → blocked | Dependents → unblocked (with flag) |
| Data edges | Dependents blocked | Dependents blocked (data requires artifacts) |
| Re-entry | Impossible | Via un-defer to planned |
| Worktree | Preserved (forensics) | Preserved (re-activation) |
```

## Blocked State Mechanics (D-15, FSM-05)

### Entry Conditions
A Slice or Step enters `blocked` state when:
1. **Abandon cascade (D-13):** A dependency was abandoned → automatic blocked
2. **Unresolved dependency:** A `blocks`-edge dependency is not yet `shipped`
3. **Data-edge unmet:** A `data`-edge dependency hasn't produced artifacts
4. **External condition:** Agent manually blocks via `state.{tier}.blocked` with
   a `blocked_reason` describing the external blocker

### Blocked Reason Storage
`blocked_reason` is a projector-owned frontmatter field (string, nullable):
- Set when `state.{tier}.blocked` event fires
- Cleared when `state.{tier}.unblocked` event fires
- For abandon-cascade: set to "Dependency {source_id} abandoned" automatically
- For manual blocks: set to user-provided description
- Persisted in frontmatter for cross-session survival

### No Timeout Rule (D-15)
The `blocked` state has NO timeout. A Slice stays blocked:
- Indefinitely until its dependencies resolve
- Until the user defers the blocker (D-14)
- Until the user re-plans to remove the dependency
- Across daemon restarts (persisted in event store + frontmatter)
- The user may shelve the project for an undetermined time

### Unblock Detection
The scheduler/projector detects unblocking:
- On every child state change event, the projector re-evaluates blocked dependents
- If the blocking dependency transitions to `shipped` (or `deferred` for blocks edges):
  - Scheduler emits `state.{tier}.unblocked` event
  - Tier transitions: blocked → prior_state (in_progress for Slice, planning for Step)
  - `blocked_reason` cleared
- If the blocking dependency is deferred (D-14):
  - For `blocks` edges: unblock with `deferred_dep` flag
  - For `data` edges: remain blocked (data requires actual artifacts)
  - For `soft` edges: unblock (soft was advisory anyway)

### Blocked State Audit
- `blocked_reason` persists in frontmatter even after unblock (historical trail)
- Cleared when unblocked but recorded in event store as `state.{tier}.unblocked` data
- STATE.md projection displays current blocked Slices with blocked_reason

### Tier-Specific Blocked Behavior
| Tier | Can Be Blocked? | How Entered | How Exited | Blocks Children? |
|------|----------------|-------------|------------|-----------------|
| Arc | No | N/A — Arc has no blockable dependencies (D-10: same-parent, root tier) | N/A | N/A |
| Stage | No | N/A — Stage transitions to `abandoned` directly (D-13 arc-level cascade) | N/A | Abandoned Stage → child Slices blocked |
| Slice | Yes | 1. Dependency abandon (auto) 2. Manual block 3. Dep not yet shipped | Blocked→in_progress (unblock) | Blocked Slice → child Steps remain in current state (not auto-blocked) |
| Step | Yes | 1. Manual block 2. External condition | Blocked→planning (unblock — may need re-plan) | Blocked Step → sibling Steps unaffected (serial run, agent handles) |

## Decimal Insertion Protocol (D-16, FSM-04)

### Purpose
Gap-closure and unexpected problems: insert work mid-stream without renumbering
the entire parent container. Decimals fill gaps between existing sequential IDs.

### Supported Format
- Single decimal level: `slice-12.1`, `slice-12.2`, `slice-12.354`
- NO cap on the decimal number (practical limit ~999 but not enforced in schema)
- Prefix preserved: `slice-` is always present (D-01)

### Prohibited Format
- Double decimals: `slice-12.1.2` — REJECTED at schema validation
- No leading zeros in integer part: `slice-012` invalid (D-01)
- No leading zeros in decimal part: `slice-12.01` valid (typical use) but `slice-12.1` preferred

### Insertion Rules
1. **Same-parent only:** Decimal inserts share the same parent as the gap they fill.
   - `slice-12.1` has the same parent Stage as `slice-12` and `slice-13`
2. **No renumbering:** Existing IDs are immutable. Adding `slice-12.1` does NOT
   change `slice-13` to `slice-14`. The decimal fills the gap, leaving all other
   IDs untouched.
3. **Sequencing:** Decimal inserts are sequenced BETWEEN the base ID and the next
   integer. `slice-12.1` logically precedes `slice-13` but follows `slice-12`.
   Scheduler treats decimals as interleaved within the integer sequence.
4. **Multiple inserts:** Multiple decimals can fill the same gap:
   `slice-12.1`, `slice-12.2`, `slice-12.3` all between `slice-12` and `slice-13`.
5. **Depends on decimals:** Dependents can reference decimal IDs normally:
   `depends_on: [{id: "slice-12.1", edge: "blocks"}]`. Decimal IDs are first-class.

### Applies To
| Tier | Decimal Support | Rationale |
|------|----------------|-----------|
| Arc | No | Too coarse; if you need to insert an Arc, create a new one at the end |
| Stage | Yes | Gap-closure at Stage level (e.g., missed auth provider) |
| Slice | Yes | Primary use case — gap-closure and unexpected problem Slices |
| Step | Yes | Sub-steps (1.1, 1.2) within a single step file (D-04); agent-managed |

### Structural Reorganization Threshold
When should you create a NEW Slice/Stage instead of inserting a decimal?
- **New Slice:** When the gap is large (≥3 missing Slices) → create new Slices at end of Stage
- **New Stage:** When the gap spans multiple Slices with different concerns → create new Stage after existing
- **Decimal preferred:** When the gap is small (1-2 items), tightly related to existing work,
  and inserting at the gap location maintains logical ordering
- **Threshold is advisory:** The user decides. The protocol SUPPORTS either approach.

### ID Validation Regex
```
Arc:    ^arc-\d+$
Stage:  ^stage-\d+(\.\d+)?$      # decimal optional
Slice:  ^slice-\d+(\.\d+)?$      # decimal optional
Step:   ^step-\d+(\.\d+)?$       # decimal optional (sub-steps)
```
Single decimal level only — two decimal dots rejected at schema validation.

### Index.json Resolution
Decimal IDs resolve via index.json the same as integer IDs:
```json
{
  "slice-12.1": "arcs/arc-07/stages/stage-03/slices/slice-12-oauth-debug/",
  "slice-12.2": "arcs/arc-07/stages/stage-03/slices/slice-12-token-refresh-fix/"
}
```
No special resolution logic needed — index.json handles all IDs uniformly.
