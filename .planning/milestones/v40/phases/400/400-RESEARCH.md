# Phase 400: Tier Definitions & State Machines - Research

**Researched:** 2026-05-06
**Domain:** Four-tier hierarchy state machine design, pydantic schema modeling, event taxonomy specification
**Confidence:** MEDIUM — locked decisions provide strong constraints, but state budget inconsistencies between CONTEXT.md and REQUIREMENTS.md require resolution; architectural precedent exists in shipped code.

## Summary

Phase 400 produces the design specification documents for the four-tier product hierarchy (Arc → Stage → Slice → Step). This is a **design-phase milestone** — output is architecture documents (per-tier specification files, state transition tables, pydantic frontmatter schemas, and event taxonomies), not implementation code. The rename of "Phase" to "Stage" (D-01) is a LOCKED decision that cascades through all output documents and the existing schema.py event definitions.

**Primary recommendation:** Use pydantic>=2.13.3 with `extra="forbid"` for all frontmatter schemas (consistent with existing codebase convention in `src/state_core/schema.py`). Model state transitions as per-machine tables with explicit guard conditions per the CONTEXT.md budgets. Separate agent-owned fields from projector-owned fields at the field level (TIER-07). Document the Phase→Stage rename migration path for all existing aggregate type literals and event type strings that currently use "phase."

The existing codebase already defines all four aggregate types (`arc`, `phase`, `slice`, `step`) in `src/state_core/schema.py` with 34+ event data payload models using `extra="forbid"` and `frozen=True`. The StepMachine skeleton in `src/state_build/kernel.py` defines the step state Literal but has no transition logic. The projector (`src/state_core/projector.py`) has 19 handlers but only three cache tables (`steps`, `slices`, `concepts`) — Arc/Phase projection handlers and cache tables must be specified in this phase but implemented in v41+ (out of scope for v40 design-only).

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| State machine definition | Per-tier spec docs | — | Each tier defines its own FSM independently |
| Cross-tier composite events | Daemon (projector) | Schema | Projector computes child-state rollup, emits parent events |
| Frontmatter schema modeling | Per-tier spec docs | Pydantic models | Design contract; runtime validation is v41+ |
| Agent-owned field writes | Agent actions | — | Agent writes ARC.md/STAGE.md/SLICE.md frontmatter fields |
| Projector-owned field writes | Daemon projector | — | Projector writes status, completed_at, child-ID arrays |

| Event taxonomy | Per-tier spec docs | schema.py extension | New event types extend existing Literal unions |
| Composite state computation | Projector | CQRS read model | Not explicit machine states; computed from child states |

## User Constraints (from CONTEXT.md)

### Locked Decisions

- **D-01:** Dash-prefix, no leading zeros: `arc-45`, `stage-22`, `slice-12`, `step-5`. Prefix always present and lowercase. The tier formerly called "Phase" is now **Stage** to avoid confusion with workflow "phases" (design phase, run phase, verify phase).
- **D-02:** Kebab-case display slugs in folder names: `arc-45-auth-system/`, `stage-22-oauth-migration/`, `slice-12-anthropic-oauth/`. Slugs are optional display fields, not part of the stable ID. ID resolution works with or without the slug.
- **D-03:** "discuss" → "design" everywhere: `/state-design-slice`, DESIGN.md. "execute" → "run" everywhere: `/state-run-slice`.
- **D-04:** Steps are markdown FILES (`step1PLAN.md`, `step2PLAN.md`...), NOT folders. Steps are generated by the run phase as tracking files. Steps can contain sub-steps (1.1, 1.2, 1.3) within a single file. Slice is the terminal container — the Slice folder holds ALL step files and workflow documents.
- **D-05:** New artifacts: CRIT.md (must-have criteria, replaces REQUIREMENTS) at Arc and Stage levels. MAP.md at Arc and Stage levels. Slice-level: DESIGN.md, RESEARCH.md, stepNPLAN.md (N files), VERIFICATION.md, SUMMARY.md. Optional sub-flows: review, lock-in, ship produce additional tracking files in the Slice folder.
- **D-06:** Slice workflow order: design → research → run (generates step files) → verify → summary → optional review/lock-in/ship sub-flows.
- **D-07:** Command style: `/state-new arc`, `/state-new stage` (tier as argument for `new`). `/state-design slice 12`, `/state-run slice 12` (tier fused into command for action commands). `/state-new stage` asks which arc interactively or takes `--arc33`.
- **D-08:** Arcs are flexible — stages can be added mid-flight while other stages are already planned/building.
- **D-09:** ID resolution: bare IDs resolve via `index.json`. Slugs for full-text search. No-arg commands use current active context.
- **D-10:** Same-parent only for dependencies. Stages can only `depends_on` stages in the SAME arc. Slices can only `depends_on` slices in the SAME stage. This keeps dependency graphs bounded and auditable per parent.
- **D-11:** Steps are NOT scheduler-dispatched. They run within one agent session. The agent is responsible for: organizing work, delegating to subagents, synthesizing work, moving to next steps, finalizing work, initiating verification and summary.
- **D-12:** `depends_on` is expressed as a frontmatter ID array with edge types: `depends_on: [{id: "slice-10", edge: "blocks"}, {id: "slice-11", edge: "soft"}]`. Edge types: `blocks` (hard prerequisite), `soft` (advisory ordering), `data` (artifact-producing, hard + artifact copy).
- **D-13:** Abandon cascade: when a Slice is abandoned, its dependents are automatically marked BLOCKED and surfaced to the user. No auto-cascade-abandon. The user must manually resolve each blocked dependent (complete the blocker, defer it, or re-plan).
- **D-14:** Deferment strategy: slices can be marked `status: deferred` with `deferred_reason` in frontmatter. Dependents treat deferred slices as soft-done — they unblock and proceed with a `deferred_dep` flag. This replaces "abandon" for intentional descoping.
- **D-15:** Blocked state has NO timeout. A Slice stays blocked indefinitely until its deps resolve or the user defers the blocker. The user may shelve the project for an undetermined time.
- **D-16:** Decimal insertions: single decimal level supported (slice-12.1, slice-12.354), no cap on the decimal number. Used for gap-closure and unexpected problems. No double decimals (12.1.2).
- **D-17:** Tier state machines (all composite states are projector-computed, not explicit machine states):
  - **Arc (≤4):** `planned → in_progress → auditing → shipped | abandoned`
  - **Stage (≤4):** `planned → in_progress → verified → shipped | abandoned`
  - **Slice (≤4):** `planned → worktree_ready → in_progress → shipped | reverted | blocked`
  - **Step (≤8):** `idle → designing → planning → running → verifying → done | blocked | abandoned`
- **D-18:** Arc `auditing` state entry guard: all child Stages are shipped. Arc ship workflow (`/state-ship-arc`): audit all stages → arc-level verification → produce ARC-SUMMARY.md → manual ship action.
- **D-19:** Composite state is computed by the CQRS projector from child states. Example: Stage is "in_progress" when any child Slice is active. Arc is "shipped" when all child Stages are shipped. No explicit composite states in the state machine — computed at query time.

### Claude's Discretion

- Exact guard condition verbosity and event naming (user approved transition tables, planner fills in details)
- Composite state computation thresholds for edge cases (e.g., "all children" vs "any children" for certain transitions)
- Pydantic field ordering within frontmatter schemas (user specified `extra="forbid"` and field classification, planner picks field order)
- Depends_on edge type exact serialization format in frontmatter (user specified content, planner picks exact YAML shape)

### Deferred Ideas (OUT OF SCOPE)

- Sub-step parallelism within a single step file (1.1, 1.2, 1.3) — the agent decides internally, no scheduler involvement. This is a v41+ harness concern, not a state machine concern.
- Optional review/lock-in/ship sub-flows at Slice level — workflow design for v41/v43, not state machine definition.
- Cross-arc dependency use cases — explicitly rejected in this phase (same-parent only). Can be revisited if a concrete use case emerges.

### Pattern 1: Per-Tier Specification Document

**What:** Each tier (Arc, Stage, Slice, Step) gets a standalone specification document that can be read without referencing other documents. Defines role, owned artifacts, behavioral primitives, and cross-tier relationships.

**When to use:** TIER-01 through TIER-05 — one document per tier.

**Example structure:**
```markdown
# Tier Specification: Arc

## Role in Hierarchy
Arc is the coarsest scoping container. It defines a feature block or project
branch containing multiple Stages. Examples: "Auth System", "Plugin Framework."

## State Machine
[transition diagram + table]

## Owned Artifacts
| Artifact | Purpose | Schema Owner |
|----------|---------|-------------|
| CRIT.md | Must-have criteria | Agent |
| MAP.md | Arc roadmap | Agent |
| ARC.md | Arc definition + frontmatter | Agent |
| STATE.md | State projection | Projector |

## Frontmatter Fields
| Field | Type | Owner | Required | Description |
|-------|------|-------|----------|-------------|
| id | str | Agent | Yes | Arc identifier: `arc-{n}` |
| title | str | Agent | Yes | Human-readable name |
| status | str | Projector | Yes | Computed from events |
| goal | str | Agent | Yes | One-line outcome |
| success_criteria | list[str] | Agent | Yes | Measurable outcomes |
| stage_count | int | Projector | No | Child Stage count |
| shipped_stage_count | int | Projector | No | Completed child Stages |

## Events
[event type table with trigger conditions and state transitions]

## Cross-Tier Relationships
- Parent of: Stages
- Sibling of: Other Arcs (via depends_on per D-10)
- Child of: None (root tier)
```

### Pattern 2: State Transition Table

**What:** Tabular format specifying every valid state transition with guard conditions, event triggers, and budget compliance.

**When to use:** FSM-01 — all four tiers need transition tables.

**Example (Stage tier, post-rename):**
```markdown
## Stage State Transition Table

| From | To | Event Trigger | Guard Condition | Budget Check |
|------|----|---------------|-----------------|-------------|
| planned | in_progress | state.stage.started | ≥1 child Slice is worktree_ready | ≤4 states |
| in_progress | verified | state.stage.slices_verified | ALL child Slices are shipped | ≤4 states |
| verified | shipped | state.stage.completed | stage-completed command with passed: true | ≤4 states |
| * | abandoned | state.stage.abandoned | Explicit abandon command | — |
| planned | abandoned | state.stage.abandoned | — | — |
| in_progress | abandoned | state.stage.abandoned | Cascade: dependents → blocked (D-13) | — |
```

### Pattern 3: Pydantic Frontmatter Schema

**What:** Each tier artifact gets a pydantic model with `extra="forbid"` and explicit field ownership classification.

**When to use:** TIER-08 — all tier artifact frontmatter models.

**Example (Stage, post-rename):**
```python
# Source pattern: src/state_core/schema.py existing models
# All use: ConfigDict(extra="forbid", frozen=True)
from pydantic import BaseModel, ConfigDict

class StageFrontmatter(BaseModel):
    """Frontmatter for STAGE.md"""
    model_config = ConfigDict(extra="forbid")

    # Agent-owned fields
    id: str                    # e.g., "arc-01/stage-03"
    title: str                 # e.g., "OAuth Provider Migration"
    goal: str                  # One-line outcome
    success_criteria: list[str]  # Measurable outcomes
    arc_id: str                # Parent Arc ID
    depends_on: list[dict]    # [{id: "stage-02", edge: "blocks"}]

    # Projector-owned fields
    status: str = "planned"    # planned | in_progress | verified | shipped | abandoned
    slice_count: int = 0       # Child Slice count
    shipped_slice_count: int = 0  # Completed child Slices
    completed_at: str | None = None
```

### Anti-Patterns to Avoid

- **Mixing agent and projector fields in the same source:** TIER-07 requires every field classified as agent-owned OR projector-owned, never mixed. Example: an agent must NOT write `status` or `completed_at` — the projector owns those.
- **Using "Phase" terminology in v40 output:** D-01 LOCKED rename to "Stage". All spec documents use "Stage" for the second tier. Cross-reference REQUIREMENTS.md which still uses "Phase" (pre-rename, needs updating).
- **Modeling composite states as explicit machine states:** D-19 requires composite states (e.g., Stage "in_progress" from child Slice activity) to be projector-computed at query time, not explicit FSM states.
- **Using paths or slugs as cross-reference targets:** D-09 specifies bare IDs resolve via index.json. All cross-references use stable IDs (`stage-22`), never paths or slugs.
- **Confusing Step as directory vs file:** D-04: Steps are FILES within the Slice folder, not subdirectories. The Slice is the terminal container.
- **Forgetting the rename in event type strings:** Existing schema.py defines `state.phase.*` events. Phase 400 specification documents should document these as `state.stage.*` events (target state) while noting the migration path from existing code.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Schema validation | Custom field validation | pydantic `extra="forbid"` | Already used in codebase for 34+ models; rejects unknown fields at parse time |

## Common Pitfalls

### Pitfall 1: Phase→Stage Rename Inconsistency
**What goes wrong:** Output documents accidentally use "Phase" when they mean "Stage," creating confusion with workflow "phases" (design phase, run phase, verify phase). The REQUIREMENTS.md still uses "Phase" throughout (pre-rename), and `src/state_core/schema.py` event types use `state.phase.*` literals.

**Why it happens:** Existing code and docs predate the rename decision. The rename was a discuss-phase decision not yet propagated.

**How to avoid:** Every output document uses "Stage" for the second tier. Include a migration note section explaining the rename from existing `state.phase.*` code. The REQUIREMENTS.md TIER-03 reference to "Phase" should be read as "Stage" for this phase.

**Warning signs:** "PHASE.md" instead of "STAGE.md"; "phase-03" instead of "stage-03"; "state.phase.planned" event without migration annotation.

### Pitfall 2: State Budget Miscount
**What goes wrong:** The Arc state list in D-17 has 5 states (planned, in_progress, auditing, shipped, abandoned) but the budget annotation says ≤4. FSM-06 in REQUIREMENTS.md says Arc max 3 states. Slice lists 6 states including terminal exits but budget says ≤4.

**Why it happens:** D-17 parenthetical annotation counts may not include terminal exit states (abandoned, reverted, blocked) in the budget. Alternatively, "auditing" may be intended as a projector-computed composite state per D-19, not a discrete machine state, reducing Arc from 5 to 4.

**How to avoid:** During planning, resolve which states count toward the budget. Recommended interpretation: exit states (abandoned, reverted, blocked) are NOT counted in the budget — only the forward progression chain counts. For Arc: planned→in_progress→auditing→shipped = 4 states (auditing IS a state per D-18, not just composite). For Slice: planned→worktree_ready→in_progress→shipped = 4 states.

**Warning signs:** Transition table shows more states than the per-tier budget; FSM-06 enforcement check fails.

### Pitfall 3: Confusing Design-Phase Scope with Implementation
**What goes wrong:** v40 is a design-phase milestone — output is architecture documents, not code. Temptation to start coding pydantic models in `src/` or modifying `schema.py`.

**Why it happens:** Familiarity with the codebase; "I already know how to implement this" — but implementation is v41+.

**How to avoid:** All pydantic models in this phase are shown as design contracts (inline code blocks in markdown), NOT as runnable Python modules. Use `python` code fences with commentary like "Schema contract — runtime validation in v41+."

**Warning signs:** Creating `.py` files in `src/`; editing `src/state_core/schema.py`; running `pytest` on spec schemas.

### Pitfall 4: Step-as-Folder Confusion
**What goes wrong:** Modeling Steps as subdirectories of the Slice folder (as GSD does for phases) instead of as flat markdown files.

**Why it happens:** GSD lineage models phases as folders with multiple files. D-04 deliberately changes this for Steps.

**How to avoid:** Steps are `step1PLAN.md`, `step2PLAN.md` etc. in the Slice folder. No `step-004/` subdirectory structure. Steps CAN contain sub-steps (1.1, 1.2) WITHIN a single file — but the file is flat.

**Warning signs:** Directory tree shows `steps/step-001/STEP.md`; step frontmatter has directory paths.

## Open Questions (RESOLVED)

1. **Arc state budget: ≤3 (FSM-06) vs ≤4 (D-17) — which is authoritative?**
   - What we know: D-17 says Arc ≤4 and lists 5 states (planned, in_progress, auditing, shipped, abandoned). FSM-06 says "Arc max 3 states." D-19 says composite states are projector-computed, not explicit machine states — suggesting "auditing" may be composite-only, leaving 4 states for the machine.
   - What's unclear: Whether "auditing" counts as a machine state (D-18 describes it with entry guards) or is purely projector-computed. Whether exit states (abandoned) count toward the budget.
   - Recommendation: During planning, propose the interpretation that "auditing" IS a machine state (4 forward states) per D-18 entry guard, exit states excluded from budget count. Flag the FSM-06 inconsistency for resolution by user or context update.
   - **RESOLVED:** D-17 is authoritative (Arc ≤4). "auditing" IS a machine state per D-18 entry guard (`all child Stages shipped`). Exit/terminal states (abandoned, blocked, reverted) are excluded from the forward-progression budget count. FSM-01 transition tables in 400-02 PLAN.md encode 4 forward states + exit states per this interpretation.

2. **Step event: `state.step.created` — is it implicit or explicit?**
   - What we know: The 10 existing Step events (schema.py) don't include a `state.step.created` event. The ARCHITECTURE.md Step FSM starts from `idle`. The StepMachine skeleton starts from `idle`.
   - What's unclear: Whether `idle` is the initial state set at aggregate creation (no explicit `created` event needed) or whether a `state.step.created` event transitions from none→idle.
   - Recommendation: Define `state.step.created` as a first event that sets the Step to `idle`. This is consistent with `state.arc.created` → `planned` pattern in existing schema.py. Apply same pattern to `state.stage.created`, `state.slice.created`.
   - **RESOLVED:** `state.step.created` is an explicit event transitioning Step from none→idle. Consistent with existing `state.arc.created`→planned pattern in schema.py. Applied to all four tiers: `state.arc.created`, `state.stage.created`, `state.slice.created`, `state.step.created`. Encoded in EVENT-TAXONOMY.md (400-02 output).

3. **Step run-tracking file naming: `stepNPLAN.md` vs separate files?**
   - What we know: D-04 says Steps are "markdown FILES (`step1PLAN.md`, `step2PLAN.md`...)". D-05 says Slice-level artifacts include "stepNPLAN.md (N files)". D-06 says "run (generates step files)."
   - What's unclear: Whether ALL step tracking is in a single `stepNPLAN.md` format (one per step) or whether Steps also generate separate DESIGN.md, VERIFICATION.md files within the Slice folder. The naming convention for N (numeric, zero-padded?) is unspecified.
   - Recommendation: Per D-06 workflow order, Steps are generated during the RUN phase. Each step produces one tracking file. Naming: `step1PLAN.md`, `step2PLAN.md` (no zero-padding, matches D-01 no-leading-zeros convention). DESIGN.md and VERIFICATION.md are Slice-level (not per-Step) artifacts.
   - **RESOLVED:** Step tracking files named `step1PLAN.md`, `step2PLAN.md` (no zero-padding per D-01). DESIGN.md and VERIFICATION.md are Slice-level artifacts, not per-Step. Encoded in TIER-STEP.md and TIER-SLICE.md (400-01 output).

4. **`state.stage.*` event migration path from `state.phase.*`**
   - What we know: Existing schema.py defines `PHASE_EVENT_TYPES` with `state.phase.*` literals (lines 73-81). D-01 locks the rename to "Stage." ARCHITECTURE.md uses "phase" throughout.
   - What's unclear: Whether Phase 400 spec documents should use `state.stage.*` event names (forward-looking design contract) or `state.phase.*` (matching current code). Whether a migration table is in-scope for v40 or deferred to v41+.
   - Recommendation: Use `state.stage.*` in all spec documents (forward-looking). Include a "Migration from Phase to Stage" appendix documenting the 1:1 mapping of all existing `state.phase.*` events to their `state.stage.*` equivalents. The actual code migration is v41+.
   - **RESOLVED:** All spec documents use `state.stage.*` (forward-looking design contract). EVENT-TAXONOMY.md includes a "Migration from Phase to Stage" appendix with 1:1 mapping of all existing `state.phase.*` events. Actual schema.py code migration is v41+.
