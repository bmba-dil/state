  **SECTION 2: Cross-Reference Format (REF-01):**

  **Depends-On Frontmatter Format (per Phase 400 D-12):**
  ```yaml
  depends_on:
    - {id: "slice-10", edge: "blocks", hash: "sha256:abc123..."}
    - {id: "stage-02", edge: "soft"}
    - {id: "slice-09", edge: "data", hash: "sha256:def456..."}
  ```
  Fields:
  - `id` (required): Short-form aggregate ID — `slice-10`, `stage-02`, `arc-03`. Must match D-01 format.
  - `edge` (required): One of `blocks`, `soft`, `data` — matching scheduler EdgeKind exactly.
  - `hash` (optional): SHA-256 content hash of target artifact at creation time. Pinned for change detection. Omitted if target doesn't support hashing.

  **ID Resolution Algorithm (from RESEARCH.md lines 433-451):**
  ```
  resolve_id(id: str) -> Optional[Path]

  1. Parse ID to extract tier prefix: arc-, stage-, slice-, step-
  2. Look up full ID in index.json under the appropriate tier section (O(1) dict lookup)
  3. If found: return entry.path. Cache result for subsequent lookups.
  4. If not found but valid format (matches D-01 regex): return None (unresolved → W004)
  5. If invalid format: return None (malformed ID → W004)

  Cache invalidation: index.json event_sequence change clears cache
  ```

  **Content-Hash Pinning (REF-01 requirement):**
  - When artifact A creates a cross-reference to artifact B, A records B's current `content_hash` from index.json in the depends_on entry
  - Purpose: detect if target changed after reference was created
  - On consistency check: compare index.json's current content_hash for target against pinned hash in reference
  - Hash mismatch severity: WARNING if target is in a mutable state (planned, designing, planning), INFO if target is in an immutable state (shipped, done, abandoned)
  - Rationale: mutable targets can legitimately change; immutable targets should not
  - Hash is SHA-256 of full file content (not just frontmatter) — covers body prose changes

  **Execution Timing (3 trigger points):**

  | Timing | Scope | Behavior |
  |--------|-------|----------|
  | Daemon startup (D-401-17) | Full check — all artifacts | Runs BEFORE HTTP server binds. If daemon_startup_blocked == true → daemon auto-launches resolution workflow, does NOT bind HTTP. |
  | Post-state-change (every state.* event) | Incremental check — only artifacts affected by the event | Runs after projector processes event. Only checks the artifact whose state changed (and its dependents). W004/W005/W011 check affected cross-references. |

  **Authority Rule (REF-06 requirement):**
  On any mismatch between filesystem state and event store state: **event store is authoritative.** The projector rebuilds all projections (STATE.md, index.json) from the event stream. Filesystem state is a cache that can be regenerated. This rule applies to W013 and W015 specifically.

  **Auto-Resolution Path (D-401-17):**
  When ERROR-severity codes block daemon startup:
  1. Daemon collects all ERROR Finding objects into a resolution context (JSON or structured object)
  2. Daemon auto-launches a resolution session (opencode subagent) with the resolution context as input
  3. Resolution session iterates findings, for each:
     - W001: removes orphan index entries
     - W006/W007/W009: reconciles hierarchy from event stream
     - W004: surfaces to user for resolution (reassign/defer/remove — per D-401-15)
     - W008/W014/W015: triggers projector full rebuild from event stream
     - W010: validates edge type against scheduler EdgeKind — reports corrupt reference to user
     - W011: breaks cycle by removing the most recent edge (surfaces to user for confirmation)
     - W012: flags cross-mode reference — surfaces to user (likely misconfiguration)
  4. Resolution session restarts daemon after all ERROR findings are resolved
  5. If resolution session fails (e.g., unresolvable W015 where event stream is corrupted): daemon reports the error, writes a crash report to `.state/build/crash/`, and exits
  6. NOT a deadlock — user can still invoke `state build health --force` to start daemon with ERRORS logged but not blocking
