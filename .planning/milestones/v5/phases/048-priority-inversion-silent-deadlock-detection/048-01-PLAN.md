Add three functions after the existing code (before the DAGScheduler class at line 395, or at the end before the class):

### `_critical_path_nodes(nodes, edges, *, edge_kinds) → set[str]`
Compute nodes on the critical path (longest chains through the DAG) using standard
Critical Path Method (CPM) with DP on topological order.

Algorithm:
1. Build adjacency restricted to `edge_kinds` (default `{"blocks", "data"}` — soft excluded)
2. Run `topo_sort()` to get deterministic ordering
3. Forward pass: DP to compute longest distance from any root to each node
   - `dist[node_id] = 0` for roots (in-degree=0)
   - `dist[target] = max(dist[target], dist[source] + 1)` for each edge
4. Find `max_dist = max(dist.values())`
5. Backward pass (reverse topological order): nodes where `dist[node] + reverse_dist[node] == max_dist + 1` are critical
   - Simplified: nodes at max distance are critical, and backtrack from terminal nodes to roots to build the full critical set
   - Actually: use reverse DP. `rev_dist[node_id] = 0` for terminals (out-degree=0 after kind-filter). Then `rev_dist[source] = max(rev_dist[source], rev_dist[target] + 1)`.
   - Node is on critical path iff `dist[node] + rev_dist[node] == max_dist + 1`.
6. Return `set[str]` of node IDs on critical path.

Complexity: O(V + E).

### `detect_priority_inversion(nodes, edges) → list[dict[str, Any]]`
Detect nodes in the frontier that are blocked only by `soft` edges and are on the critical path.

Algorithm:
1. Compute frontier via the existing `frontier()` function (already ignores soft edges)
2. Compute critical path nodes via `_critical_path_nodes(nodes, edges)`
3. For each node in frontier:
   a. Find all soft edges targeting this node where the source is NOT done
   b. If any such soft edges exist AND the node is in the critical path:
      - Record: `{"node_id": node.id, "soft_edges": [e.source_node for e in blocking_soft], "critical_path": True}`
4. Return the list of detection records (empty if none detected).

### `detect_silent_deadlock(nodes, edges) → dict[str, Any] | None`
Detect when the frontier is empty, in-progress nodes exist, and ALL in-progress nodes are
blocked on missing or descoped predecessors.

Algorithm:
1. Compute frontier via `frontier()`. If NOT empty → return None (work is dispatchable).
2. Find all nodes with `status == "in_progress"`. If none → return None.
3. Build set of all node IDs from `nodes` list for membership testing.
4. For EACH in_progress node:
   a. Find ALL blocking edges (blocks, data) targeting this node
   b. For each such edge, check the source node:
      - If source not in node set → "missing"
      - If source status is `"failed"` or `"blocked"` → "descoped"
      - If source status is `"done"` → predecessor satisfied (skip)
      - Otherwise (idle, pending, in_progress) → predecessor still reachable (legitimate wait)
   c. If the in_progress node has at least one missing or descoped predecessor AND NO
      reachable (non-done, non-missing, non-descoped) predecessor → this node is "stuck"
   d. If the in_progress node has at least one reachable predecessor → NOT stuck
5. If ALL in_progress nodes are stuck:
   - Collect all deadlocked node IDs
   - Collect unique missing predecessor IDs across all stuck nodes
   - Collect unique descoped predecessor IDs across all stuck nodes
   - Return `{"deadlocked_nodes": [...], "missing_predecessors": [...], "descoped_predecessors": [...]}`
6. If ANY in_progress node is NOT stuck → return None (not a full deadlock).

| Boundary | Description |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-048-01 | Spoofing | `on_scheduler_event` callback | mitigate | Callback is injected by the daemon orchestrator (trusted context). Detection results are typed through Pydantic models before reaching the event store — malformed data fails at `model_dump()` boundary. |
| T-048-02 | Denial of Service | DAGScheduler.tick() diagnostics | mitigate | Post-tick diagnostic block is wrapped in try/except — any exception (including infinite loop from malformed DAG) is silently caught. Diagnostics failure never blocks scheduling. |
| T-048-03 | Information Disclosure | Deadlock event payload | mitigate | `SchedulerDeadlockData` only carries node IDs and predecessor IDs — no credentials, file paths, or PII. Event data is safe to log and mirror to opencode SyncEvent. |
| T-048-04 | Tampering | Critical-path computation | accept | An attacker who can modify the DAG edges already controls scheduling decisions. Critical-path is a heuristic diagnostic, not a security control — its tampering has no security impact beyond mislabeling warnings. |
</threat_model>
