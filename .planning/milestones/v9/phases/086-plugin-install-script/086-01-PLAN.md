```typescript
// ── 0. First-run auto-install ──────────────────────────────────────────
if (meta.state === "first") {
  // Auto-register the plugin itself using TuiPluginInstallOptions API
  api.plugins.install("@state/opencode-plugin", { global: false })
    .then((result) => {
      log({
        source: "@state/opencode-plugin/tui",
        event: "tui.install.plugin",
        state: meta.state,
        result,
      });
    })
    .catch((err) => {
      log({
        source: "@state/opencode-plugin/tui",
        event: "tui.install.plugin.error",
        error: String(err),
      });
    });

  // Auto-register MCP servers
  for (const name of ["state-build", "state-teach"] as const) {
    api.client.mcp.add({
      body: {
        name,
        config: {
          type: "local",
          command: [name],
          enabled: true,
        },
      },
    })
      .then((response) => {
        log({
          source: "@state/opencode-plugin/tui",
          event: "tui.install.mcp",
          mcp: name,
          response: response.data,
        });
      })
      .catch((err) => {
        log({
          source: "@state/opencode-plugin/tui",
          event: "tui.install.mcp.error",
          mcp: name,
          error: String(err),
        });
      });
  }
}
```

**Key design decisions:**
- Uses `.then()/.catch()` pattern (not `await`) so MCP registration never blocks theme installation or slot registration. The existing `install.sh` is a blocking bash script; the TUI install must be non-blocking.
- Uses `api.plugins.install()` per the user requirement to use `TuiPluginInstallOptions` API. The `{ global: false }` installs at project level.
- MCP server commands are `["state-build"]` / `["state-teach"]` — these name-match the Python entry points defined elsewhere in the monorepo. The MCP daemon will start them when the commands become available.
- Errors are logged but never thrown — plugin load must succeed even if MCP registration fails (handles already-registered and network-unavailable cases).

**Do NOT:**
- Use `await` for the install calls (must be non-blocking)
- Hardcode paths to the plugin directory
- Throw on install errors
- Remove or modify any existing logic (theme, slots, SSE)

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Plugin→Daemon (MCP add) | Plugin calls `api.client.mcp.add()` which routes through opencode daemon HTTP API to modify `opencode.json`. MCP server commands (`state-build`, `state-teach`) executed by daemon. |
| Plugin→Daemon (Config update) | Plugin calls `api.plugins.install()` which modifies `opencode.json` plugin array via daemon. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-086-01 | Elevation | `tui.ts` createTuiPlugin | mitigate | The plugin runs with the daemon's authority (same process context). `api.client.mcp.add()` is authenticated by the daemon's existing session token — no extra auth needed. The MCP server commands (`["state-build"]`) are fixed strings — no user input influences command execution. |
| T-086-02 | Tampering | MCP server registration | mitigate | `api.plugins.install()` and `api.client.mcp.add()` go through daemon HTTP API which validates request bodies against the Config/Mcp schema. Malformed `opencode.json` from external tampering would be caught by schema validation on next daemon start. |
| T-086-03 | Denial of Service | First-run MCP registration | accept | Two `api.client.mcp.add()` calls on first load are fire-and-forget (`.then()/.catch()` not `await`). Cannot block plugin load or daemon startup. The `for` loop iterates over a fixed 2-element array — no unbounded operations. |
</threat_model>
