    **Architecture (module-level state pattern — same as sidebar-content-renderer.ts):**

    **Exports (5):**

    - `renderBuildProgress()` — returns renderable tree (Box) for the current state
    - `stepStatusColor(status: StepStatus)` — pure function: maps status to hex color

    **Types (internal — all exported via the module):**
    ```typescript
    type ConnectionStatus = "connected" | "disconnected" | "unreachable";
    type StepStatus = "pending" | "running" | "done" | "blocked" | "retry" | "unknown";
    
    interface BuildProgressState {
      connection: ConnectionStatus;
      sessionStatus: SessionStatus | null;
      sessionID: string | null;
    }
    
    interface DagNode { id: string; name: string; status: StepStatus; }
    interface DagEdge { from: string; to: string; }
    ```

    **Implementation details:**

    1. **State initialization** (`BUILD_PROGRESS_STATE`):
       - Initial value: `{ connection: "unreachable", sessionStatus: null, sessionID: null }`
       - `connection` starts as `"unreachable"` — transitions to `"connected"` on first `session.status` event
       - No timeout/heartbeat mechanism needed (SSE handles reconnection internally)

    2. **`setupBuildProgress(api)` — event wiring:**
       - Subscribe to `api.event.on("session.status", handler)`
       - Handler updates `BUILD_PROGRESS_STATE.sessionStatus` and `BUILD_PROGRESS_STATE.sessionID`
       - On first event received: set `connection` to `"connected"`
       - Register cleanup via `api.lifecycle.onDispose(fn)` — call the unsubscribe function + reset state

    3. **`renderBuildProgress()` — main render:**
       Returns a `Box({ flexDirection: "column" })` with the following sections:
       
       **A. Step status row** (1 cell tall):
       - Derive step status from `sessionStatus`:
         - `null` → `"unknown"` (no events received yet)
         - `{ type: "idle" }` → `"done"` (previous step completed, no active step)
         - `{ type: "busy" }` → `"running"` (current step executing)
         - `{ type: "retry" }` → `"retry"` (step retrying)
       - Format: `{color-dot} Step: {status_label}` where color-dot is `●` (U+25CF) in the status color
       - Status labels: running→"Running", done→"Idle", retry→"Retrying (attempt N)", blocked→"Blocked", unknown→"Waiting"
       - If `sessionID` is set, append truncated session ID: `Step: Running · s:abc123…`
       - Use `Txt()` helper with appropriate `fg`, `attributes` (bold for status label)

       **B. Divider** (1 cell tall):
       - 28 `─` characters (U+2500) with `fg: T.border`, consistent with sidebar-content-renderer pattern
       - Rendered as: `Txt({ fg: T.border, height: 1 }, "\u2500".repeat(28))`

       **C. DAG area** (variable height, 28 cells wide):

Since real build-kernel events (v14+) don't exist yet, use a static placeholder DAG that demonstrates the rendering: a 2-node, 1-edge DAG showing Slice nodes with status colors. The placeholder DAG should look realistic:

         ```
         └──────────────────────────┘
         ```
         Where `●` = done (success), `◉` = running (accent), `○` = pending (muted).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Event bus → Component | `api.event.on("session.status")` delivers events from the daemon SSE relay — event payloads cross trust boundary (daemon may send malformed events, unexpected status types) |
| Filesystem → Component | None — BuildProgress does not read any files from disk. All data comes from the event bus. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-082-01 | Spoofing | `session.status` event handler | accept | Events come from opencode's internal event bus, which is populated by the daemon's authenticated SSE stream. Daemon auth (OAuth/API-key) provides trust. No additional event origin verification needed at the UI layer. |
| T-082-02 | Tampering | `BUILD_PROGRESS_STATE` mutation | mitigate | State is module-level but only mutated by the event handler registered via `setupBuildProgress`. No external write path exists. The exported `BUILD_PROGRESS_STATE` const is type-annotated to prevent accidental shape mutations. |
| T-082-03 | Information Disclosure | `renderBuildProgress` output | mitigate | Rendered text uses truncated session IDs (max 8 chars shown). Raw event payloads are never rendered — only derived status labels and step names. Internal error details (event parse failures) are logged to console but not rendered in the TUI. |
| T-082-04 | Denial of Service | High-frequency `session.status` events | accept | The render function is called at opencode's frame rate (~60fps). State updates are O(1) assignments. No DOM, no heavy computation — the DAG box-drawing is pure string formatting of <5 nodes. Cannot DOS the render pipeline. |
| T-082-05 | Elevation of Privilege | Component render path | accept | The component only reads state and renders UI. It does not call any state-changing APIs (no auth, no command execution, no filesystem writes). No privilege escalation possible through this render path. |
</threat_model>
